# 镜头描述必须兑现为实际动效

本页规定导演怎样描述、交接和审查运动；算法、曲线、参数和执行器只在定位到的 FOUNDATION 的 motion 模块维护。适用于新增或修改的镜头，已有工程仅改受影响范围。

## 先用动态规范决定观看过程

写镜头描述前，先使用 FOUNDATION 的 `modules/motion/library.html`，或运行 `python modules/motion/library.py --intent 目的`。按突出重点、转换关注、交代空间、内容交接、事件强调、稳定阅读选型；默认聚焦当前后端可调用的常用项。只读取选中项指向的调用合同、曲线及动态预览，不先通读全部执行器和研究记录。待接入设计与旧配方按需显式展开，设计ID不能写作recipe。完整选型规则见 FOUNDATION `modules/motion/SELECTION.md`。

HTML 结构用来理解层级、焦点和运动；pulse系列预览与正式执行器共用曲线，GSAP设计试样尚不因此获得正式能力。静态图只补充构图，不能作为动效兑现证据。基础技能缺失时仍可交纯设计，但须说明无法核对执行能力。

导演先判断观众此刻要看谁、看见什么变化、最后读懂什么，再选择运动。相机改变关注点，主体动作改变状态，图层组改变一组对象，转场交接相邻镜头；四者分开描述。固定镜头与直接切镜同样是有效设计，不为套用预设强行动起来。

阶段二用大白话说清“先稳住哪里 → 怎样移动或变化 → 停在哪里、留下什么供阅读”，可引用 HTML 中的效果名称帮助理解，不把曲线参数清单交给用户填写。阶段三把已经采用的设计映射到真实能力与事件；阶段四按同一决定制作和审片。构思箭头和线性白模不能证明正式 pulse 曲线已经实现。

## 在镜头说明中确定运镜频率

阶段二写第一轮镜头说明时，按完整表达段预估时长，分别定下**整体运镜**和其中**带缩放的运镜**的档位。连续短镜头合在同一表达段统计。两项都按「该项次数 × 10 ÷ 该段时长（秒）」折算为每 10 秒的次数，用未取整值判档。

| 档位 | 每 10 秒折算次数 |
| --- | --- |
| 0 · 无 | 0 |
| 1 · 疏 | 大于 0，至 1 |
| 2 · 适中 | 大于 1，至 2 |
| 3 · 密 | 大于 2，至 3 |
| 4 · 很密 | 大于 3 |

一次有独立观看目的的相机运动计一次。同一次运动如果边横移边推近，整体与带缩放各计一次。切镜、人物动作和组件变化另行描述。

10 秒是比较频率的换算单位，每段的实际次数由观看任务决定。写清每次运动的触发与落点，以及固定时观众要看的内容。阶段三按更新后的时长复核档位。运动是否挤在一起、落稳后是否来得及阅读等必须连续观看才能判断时，用最简动态白模复核。需要定位局部扎堆时，看连续 10 秒内的运镜起点数。持续移动较久时另记持续时间。

## 每个采用的运动要能回答这些问题

| 决定 | 镜头描述与交接必须说明 |
| --- | --- |
| 解释任务与焦点 | 为什么动；先看谁、再看谁；相机关注点和对象身份，不只写“高级运镜” |
| 运动层级与范围 | 相机、主体、内容组或跨镜转场；哪些一起动，哪些保持，包括标题、字幕与背景 |
| 起态、过程、落点 | 起始构图／状态，路径或方向，终点景别／状态；相机推近不能代替主体发生变化 |
| 时间与曲线 | 起动与可见触点、收束窗口、采用的曲线或预设，以及后续稳定阅读 |
| 接镜与素材边界 | 前镜交出、过程、后镜接住和落稳；关注点、遮挡、背景余量与 free/cover 边界是否支持构图 |
| 实现与验收 | 对应的实际 recipe／参数或明确的待补能力，正常速度应看到的结果及具体失败判据 |

固定镜头写明固定机位、对象事件和稳定阅读。按实际配乐校准选定触点，配乐待定时标预估。新能力通过实际调用和可播放试样验证。

## 从描述到唯一执行源

例如：“先看完整流程；讲到结果时，镜头短促推向结果对象，快速起步、逐渐收住；随后固定，数值改变并留给观众阅读，字幕保持屏幕位置。”

进入制作时，在现有创作源中对应记录：

- `visual.action / continuity` 与 `intent` 保存观看意图、固定层及验收结果；不新增第二份镜头描述源。
- `storyboard` 的既有事件保存触发、完成及阅读时间。将所选配乐拍点换算到当前工程帧。
- `production-plan` 的既有 motions 引用 `motion.camera-pulse.v1`、kind=push、关注点、倍率和 out 曲线，按项目 fps 换算时长；多段相机选 path，震动另列；主体状态变化另由 scenes/components 实现。
- `handoff` 后核对生成的 VideoSpec 确实含有采用的 recipe、目标、曲线和事件窗口。工作台修改后，当前项目 JSON 是剪辑源，最终按该分支重新验收。

参数与默认值从 FOUNDATION 的规范读取，不在导演层另抄一份曲线表或数值表。HTML 复制出的 JSON 是基础输入示例，需映射到当前导演源和实际事件，不能直接替代交接。

## 制作与审片按同一要求验收

从实际工作台导出并正常速度播放，核对关注对象与终点构图、动作窗口、曲线的启动／超调／收回、落稳后的阅读、固定层和转场承接。检查相邻镜头与实际配乐触点，变速、裁入或素材替换后重查。

期望用 slam 却只做线性放大、要求短促运动却整句缓推、要求内容组移动却整幅画面平移、要求页面接续却直接淡化，均记为未兑现，先修复，不能用“差不多”或导出成功代替通过。确有后端或素材限制时先做可播放试样并说明调整依据；未经确认，不静默替换已采用的关键效果。

沿既有 Review 保存镜号／clipId、期望与实际、成片时间区间和播放证据，绑定当前导出 JSON 与 MP4。静帧可查落点，不能证明曲线和运动观感；未播放记未审。用户本次确认的是这套工作方式及持续要求，不等于已认可每个参数或所有试样的美术观感。
